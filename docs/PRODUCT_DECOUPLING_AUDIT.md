# LelloStore deployment decoupling audit

This is the baseline audit, preserved for traceability. Several findings have since been addressed; see [implementation progress](PRODUCT_SPEC.md#acceptance-and-progress) for current status.

LelloStore can become a reusable client and self-hosted server without changing its product identity. The main blockers are Android authentication bound to LelloAuth, state shared across server selections, frontend configuration embedded at build time, and an Android dependency resolved from a sibling checkout. The target is one distributable client and one server image, with `store.lelloman.com` configured as an ordinary deployment.

This assessment covers the tracked Android modules, backend, frontend, migrations, scripts, CI, Docker configuration, and documentation as of October 8, 2026. Findings describe source behavior; clean-machine builds and deployment migration remain acceptance work. Ignored local credentials, live infrastructure, and Git history are outside this audit.

The [product roadmap](PRODUCT_ROADMAP.md) extends this audit into backend onboarding, Android server/QR setup, generalized authentication, a later rename and public release, and conversion of this repository into deployment configuration. Its sequencing and product decisions take precedence over the initial implementation proposal below.

The session finding has a concrete consequence: saving another HTTPS server while authenticated can send the old bearer token to that server. The shared HTTP client also serves images in [LelloStoreApplication.kt](../android/app/src/main/java/com/lelloman/store/LelloStoreApplication.kt), while [RemoteApiClientImpl.kt](../android/remoteapi/src/main/kotlin/com/lelloman/store/remoteapi/RemoteApiClientImpl.kt) preserves absolute icon URLs. Restricting credentials by destination matters independently of whether the server selector is visible.

## Deployment assumptions to make explicit

**Authentication is required today.** Production catalog routes fail closed without OIDC, and the web router requires login. That is a valid self-hosted product model. Anonymous catalogs would be a separate feature affecting authorization, acquisitions, and client flows; removing the personal issuer does not require adding them. Backend audience, admin role, and claim path are already configurable. Android uses fixed default scopes and the web requests `offline_access`; supported provider setup should document client registration, redirect URIs, scopes, and access-token audience requirements.

**Each backend database assumes one configured issuer.** Catalog access tables and acquisition ownership commonly use `subject` alone, as seen in [access migrations](../backend/migrations/2026090201_app_access.sql) and [acquisition migrations](../backend/migrations/2026092202_acquisitions.sql). That works with one issuer per deployment, but reusing the database with a different issuer needs an identity migration or a guard. Matching `sub` strings from two providers must not silently inherit access.

**Hosting assumes an origin root in several places.** The web callback is `window.location.origin + /callback`, routing uses `createWebHistory()` without a base, and push configuration explicitly requires an HTTPS origin. Android's URL validator accepts broader URLs, including paths. Either document and consistently enforce an origin-only server URL or implement path-prefix support across clients, callbacks, API routes, and push. Normalize URLs and reject credentials, queries, and fragments where unsupported.

**Capabilities need discovery.** Push can already be disabled with `NOTIFICATIONS_ENABLED`, and Paravoid signing is optional through `PARAVOID_SIGNING_CONFIG`. The public client should learn supported capabilities from the selected server so unavailable features have a clear state. [NotificationBrokerRuntime.kt](../android/app/src/main/java/com/lelloman/store/notification/NotificationBrokerRuntime.kt) already binds device identity to server URL, issuer, and subject; integrate its registration reset/reconnect behavior with the server-switch operation.

**Signing belongs to the distribution channel.** The app unconditionally bundles the recovery release APK. [RecoveryContract.kt](../android/recovery-protocol/src/main/kotlin/com/lelloman/store/recovery/protocol/RecoveryContract.kt) fixes product package IDs, and the recovery client checks matching app/companion signatures. [RecoveryCompanionClient.kt](../android/app/src/main/java/com/lelloman/store/recovery/RecoveryCompanionClient.kt) also requires a single-APK installation for recovery provisioning. Preserve trust checks; design any separately signed or split-APK distribution deliberately, potentially with an optional recovery build feature. Server operators should not need the product's Android signing key.

**Release builds depend on full Git history.** The app derives version codes from commit count and rejects shallow repositories. This is a release-process assumption, not a dependency on the live store. Support explicit release version inputs if source archives or external builders are intended, while maintaining monotonic version codes for the existing app.

**Publishing configuration is mostly separated already.** [publish-to-lellostore.py](../scripts/publish-to-lellostore.py) requires store URL, issuer, and client ID through flags/environment and performs OIDC discovery. Its token cache is scoped to issuer/client, not destination store or audience. Revisit that scope when supporting named deployments; shared-issuer token reuse should be intentional. The Android publishing wrapper already uses the repository-local publisher and external signing properties.

## Product identity and reusable integrations

`com.lelloman.store`, the recovery package, AIDL names, permission names, and OAuth redirect scheme identify the product and its Android contracts. They can remain while independent operators host their own backends. Renaming them would introduce installation, update, callback, and IPC compatibility work without solving deployment coupling.

Paravoid and UnifiedPush are product integrations. Paravoid runtime signing URLs and key paths are already supplied by operator configuration, and the vendored delivery tools have pinned upstream provenance in [their README](../scripts/vendor/paravoid/README.md). The build dependency needs distribution work; the protocol does not need to be removed merely because it originated in the same ecosystem. Likewise, `lelloman-simple-server` is pinned from crates.io rather than a local source path.

The backend configuration, storage paths, access groups, APK/AAB processing, and migrations do not require a particular personal hostname. The seeded `lellostore` notification sender and `all` access group are product semantics. Loopback ADB addresses and test fixtures are not production endpoints. Personal domains in Android previews/tests and a Pezzottify route test are low-priority example cleanup; the publisher's assertions forbidding hardcoded domains are useful regression checks.

The tracked repository has no project-wide license file; third-party notices do not license the product itself. Choosing a license and checking redistribution rights for dependencies and vendored sources remains a separate prerequisite for public source distribution.

## Proposed implementation order

1. Define the public bootstrap contract and backend environment settings. Preserve the current deployment through explicit values. Keep the first version to one active server and required OIDC authentication.
2. Implement Android server selection, runtime OIDC configuration, destination-bound credentials, and coordinated session/data/work cleanup. Migrate existing installations without losing their selected store.
3. Move frontend authentication to runtime bootstrap configuration. Supply complete generic operator examples for OIDC, push, and optional Paravoid settings. [The frontend auth store](../frontend/src/stores/auth.ts) prefers the backend identity response but falls back to build-time role settings; either move those settings to runtime configuration too or remove that fallback deliberately.
4. Make Android and integration builds independent of local checkout layout. Document release signing, recovery packaging, and explicit version inputs where needed.
5. Move personal defaults into deployment configuration, replace production examples, and document a fresh deployment from the same published artifacts.

Acceptance should demonstrate two independent stores with different OIDC issuers using the same APK and server image. Switching must prevent old-token requests, stale catalog writes, and old downloads/install work from crossing into the new session. Also verify interrupted login during switching, overlapping package/version identities, push-disabled operation, and upgrade behavior for existing personal-deployment installations. A clean checkout must build without private endpoints or sibling repositories.
